# batter-pose — 打擊姿態 3D 骨架

> Three.js 版；資料層在 `../bpe-data/`，本資料夾只管渲染與播放。

## 用途

把一筆 BPE 揮棒結果的 19 點骨架（COCO-17 人體 + `bat_knob`/`bat_head` 球棒兩點）逐幀播放成
3D 動畫：細線分析骨架（細線加小顆關節亮點）、四肢左右分色，球棒照真實木棒的輪廓與木紋畫出、球體帶 20 顆拖尾、本壘板與地面格線當參照，
深淺兩套畫布配色，五個視角（全景、打者特寫、側面、投手方向、俯視）。定位是「教練能快速判讀的揮棒分析台」：
看的人要能看清楚打者怎麼揮、前腳前手在哪、球棒在哪一幀碰到球，並把姿態跟棒速、攻擊角這些數字連起來。

registry（`app/modules/registry.ts`）裡的 `batter-pose-skeleton`（打擊姿態 3D 骨架）條目即本模組。
骨架寫法照 `pitch-pose/` 的範式（`PoseSkeletonScene`），場景外觀（圓柱球棒、白色本壘板、只畫地面的
格線、指向投手的箭頭）則照演算法端的參考實作，差別在骨架多了球棒兩點、多了球體拖尾、資料改吃 `bpe-data`。

## 檔案

| 檔案 | 責任 |
|------|------|
| `BatterSwing3d.vue` | 薄殼元件：只認 `swing` + `frame` 兩個輸入，畫面全交給 `core/swingScene.ts`；疊在畫布上的圖例、擊球標籤、操作提示、視角切換在這裡 |
| `core/swingScene.ts` | **場景本體（框架無關 class）**：骨架/球棒/拖尾/本壘板/格線/背景的 three 物件、每幀更新與取景 |
| `core/swingTheme.ts` | 深淺兩套配色（純資料）：場景與圖例共用同一份，換色只改這裡 |
| `core/skeletonStyle.ts` | 骨架的顯示角色（純函式）：依關節名稱分左半身四肢／右半身四肢／軀幹／頭部 |
| `core/ballTrail.ts` | 拖尾取樣（純函式）：目標幀 → 20 顆球各自的座標/縮放/透明度 |
| `core/swingFraming.ts` | 取景（純函式）：五個視角各自框哪些點、從哪個方向看 |
| `core/contactOffset.ts` | 相對擊球的時間（純函式）：「距擊球 −120 ms／擊球 0 ms／擊球後 +80 ms」 |
| `core/swingStats.ts` | 骨架全缺幀數、球棒缺點幀數（純函式），showcase 的「資料完整度」用 |
| `core/playback.ts` | 播放時鐘推進的純數學（不含 rAF），供 `useBpePlayback` 呼叫 |
| `../bpe-data/` | **外部依賴**：結果檔解析、缺值規則、13 項數值——必須一併帶走 |
| `../scene3d/` | **外部依賴**：three 場景樣板（Viewport 與它的 `framePoints` 取景）、hover 標籤——必須一併帶走 |
| `../baseball-field/core/fieldGeometry.ts` | **外部依賴**：`HOME_PLATE_POINTS`（貼地本壘板用）——必須一併帶走 |
| `../baseball-spin/core/normalize-model.ts` | **外部依賴**：棒球模型歸一化成單位球（與 baseball-spin 同一套算法）——必須一併帶走 |
| `public/models/baseball_detail.glb` | 棒球模型（約 700KB，與 baseball-spin 共用）；不傳 `ballModelUrl` 就用不到 |
| `app/composables/useBpePlayback.ts` | rAF 播放時鐘（Nuxt composable）——搬移時一併帶走，或自備等效時鐘 |

## 用法

```vue
<script setup lang="ts">
const { entries, selected, outcome } = useBpeEvents(0)
const swing = computed(() => (outcome.value?.ok ? outcome.value.result.swing : null))
const { frame, playing, rate, loop, toggle, step, seek, jumpToContact } = useBpePlayback(swing)
</script>

<template>
  <BatterSwing3d
    v-if="swing"
    :swing="swing"
    :frame="frame"
    :height="440"
    :dark="false"
    :ball-model-url="asset('/models/baseball_detail.glb')"
  />
</template>
```

`BatterSwing3d` 只負責畫，不持有播放時鐘；`swing` 為 `null`（沒有動畫資料）時呼叫端就不要掛載它。
逐幀操作全走播放時鐘：`step(n)` 暫停並前後移動 n 幀（±1、±10 都用它），`seek(i)` 暫停並跳到第 i 幀
（輸入框、拖曳時間軸）。本專案 showcase 另外接了鍵盤：← → 逐幀、Shift 一次 10 幀、空白鍵播放／暫停——
鍵盤是頁面層的事，不在本元件裡。
播放時鐘（`useBpePlayback`）在載入與換事件時一律停在擊球幀、不自動播放：先讓人看懂這一下在哪裡碰到球，
再自己按播放（沒有擊球點就停在第 0 幀），也順帶滿足規範的「減少動態效果偏好仍適用，不自動播放」。
`dark` 切換畫布配色（見「配色」），換配色時場景會整組重建骨架，播放中切也不會跳幀。
`ballModelUrl` 選填：給了用棒球模型畫球，不給就畫規範預設的紅球（見「拖尾規則」）。
`interactive` 預設 `true`；不能操作的縮圖傳 `false`，關掉擊球標籤、操作提示與視角切換，只留圖例
（擊球標籤在循環播放時只會閃一幀，放在預覽影片裡看起來像畫面壞掉）。
`#stats` slot 選填：放進畫布右上角的數據面板（本元件提供依畫布深淺的底板與框線，內容由呼叫端決定）。
本專案 showcase 放本次揮棒的三項核心數據，第一屏就能把姿態和數字連起來。

疊在畫布上的 HTML（都在 `BatterSwing3d.vue`，出現或消失都不會推動畫布外的版面）：

| 位置 | 內容 |
|------|------|
| 左上 | 「擊球瞬間」標籤：目前幀等於 `swing.contactFrame` 才出現 |
| 右上 | 有 `#stats` 就放數據面板（寬螢幕排一列、手機疊三行）；沒有才放操作提示「拖曳旋轉 · 滾輪縮放 · 右鍵平移」，只在寬螢幕顯示 |
| 左下 | 圖例（左半身、右半身、軀幹、球棒、球），半透明底板；色塊直接讀 `core/swingTheme.ts`。棒球模型真的換上去後「球」才畫成白球，跟畫面一致 |
| 右下 | 視角切換「全景／特寫／側面／投手／俯視」（兩個字，手機上五顆排得下，完整說明在提示），點目前這一顆也會重新取景，兼當「重設視角」 |

## 座標（不轉換）

BPE 座標系與本 repo 的 `spec/domain/baseball-field-coordinates.md` 相同（原點本壘板尖端、+x 一壘、
+y 投手、+z 向上），而 `scene3d` 的相機本來就是 z-up，所以 `*_cm` 直接當世界座標（cm）用，
**不做**規範第 1 節給的 three.js y-up 換算式（`three.y = bpe.z, three.z = -bpe.y`）。多轉一次
只會讓這個模組多背一份換算規則，且與 `bpe-data`/`../scene3d` 的既有慣例（`pitch-pose`、
`pitch-trajectory` 都是原生 cm 直接當世界單位）不一致。

## 骨架與球棒

一律讀 `swing.jointNames` 與 `swing.bones`（`bpe-data` 已把骨頭依兩端是否都是 `bat_*` 分成
`kind: 'body' | 'bat'`），**不寫死索引、不引用 COCO 常數**——與 `pitch-pose` 用固定的
`COCO_KEYPOINT_NAMES`/`SKELETON_EDGES` 不同，這裡换事件時骨架數量理論上可能不同，
`SwingScene.setSwing()` 因此會整組重建骨頭/關節物件，不是只換資料。

人體依關節名稱分角色（`core/skeletonStyle.ts`，只看名稱、不看索引；認不出來的名稱歸軀幹色、照常畫）：

| 角色 | 骨頭 | 關節 | 為什麼 |
|------|------|------|--------|
| 左半身／右半身 | 兩端同側的四肢（`left_*`／`right_*`，打者自己的左右） | 肘、腕、膝、踝 | 分色才看得出前腳、前手，打擊分析最常看的就是這兩個 |
| 軀幹 | 兩端都是肩或髖（肩線、髖線、軀幹兩側），以及跨左右的線 | 左右肩、左右髖 | 中性色、不帶彩度，把人體中軸穩住，不跟手腳的顏色搶 |
| 頭部 | 任一端是 `nose`／`*_eye`／`*_ear`（含耳到肩的頸線） | 頭部五點 | 五點擠在十幾公分內，照四肢的粗細畫會糊成一團，所以細而淡 |

- 人體骨頭：兩組 `LineSegments2`（像素線寬），每幀只覆寫兩端點座標
  - 四肢與軀幹：`BODY_LINE_WIDTH_PX = 3`，逐段頂點色（左半身、右半身、軀幹三色）
  - 頭部：`HEAD_LINE_WIDTH_PX = 1.75`，單色淡灰
- 人體關節：一組 `InstancedMesh`，每個關節一顆單位球，半徑 2.3 cm（參考實作的值）、頭部 1.2 cm；
  `MeshLambertMaterial`（霧面、不反光）。顏色是所屬部位色往白色混 `JOINT_TINT = 0.45`
  （`core/swingTheme.ts` 的 `tintTowardWhite`），讀起來是同一條肢體上較亮的節點，左右仍分得出來
- 球棒：每條球棒骨頭一根木棒（`Group`：棒身 ＋ 握把布），每幀放到 knob 與 head 的中點、`scale.y` 拉成
  兩點距離、再轉到兩點方向。哪端是棒頭看名稱（含 `head` 的那端），名稱看不出來就把骨頭的 `to` 當棒頭。
  - 外型：`BAT_PROFILE` 照標準成人木棒的輪廓做旋轉體（`LatheGeometry`）——握把尾端圓頭（直徑約 4.5 cm）、
    細握把（約 2.4 cm）、漸粗過渡、打擊區（約 6.6 cm）、圓弧棒頭。長度方向依資料的兩點距離縮放，半徑固定
  - 握把布：握把段外面一層略粗的深色套筒，順便標出哪一端是握把
  - 材質：`MeshPhysicalMaterial`，木紋貼圖（沿棒身的直條紋，固定種子產生，每次載入都一樣）乘上配色的球棒色，
    外面一層亮光漆（clearcoat）；環境反射用 three 內建的 `RoomEnvironment`（`Viewport.createRoomEnvironment()`，
    只給球棒用，骨架顏色不受影響），高光沿著棒身滑動才有「上過漆的木頭」的感覺
- 球棒關節（`bat_knob`/`bat_head`）：用 `isBatJoint(name)`（`bpe-data/core/parseBpeResult.ts`，以 `bat_` 前綴判定）分流。
  畫得出木棒的那一幀，握把圓頭與棒頭本身就標出這兩點，不另外畫球；另一端缺值、畫不出木棒時，
  有效的那一點才畫成球棒色小球（規範：缺的是那一端，有值的點照畫）

骨架的畫法走「細線分析骨架」，同演算法端參考實作（`bpe-viewer.html`：1px `LineSegments` 骨頭、
Lambert 關節球半徑 2.3 cm）與專業動作分析軟體的風格：細線俐落、關節是小亮點。曾經試過打光的粗圓柱
（半徑 2.4 cm），每段一樣粗又帶反光，看起來像塑膠吸管——不像分析工具那樣俐落，也沒有人體的體積，所以換回細線。

線寬用像素、不用公分：1 cm 粗的線在全景下只剩 1px 左右，會閃爍；像素線寬在五個視角、滾輪縮放下都一樣俐落。
參考實作是 1px，retina 螢幕上太細；試過 2px 仍偏細，取 3px。代價是線本身沒有明暗，前後深度靠關節球的明暗、左右分色與快捷視角判斷。
所有線寬、半徑、木棒外型都是**顯示設定，不是量測值**——資料只有關節中心點與球棒兩端點。

關節是 `MeshLambertMaterial`（霧面），球棒是上面的 `MeshPhysicalMaterial`，骨頭的細線不受光源影響。三盞燈：
天光（上白下石板灰，陰影面不死黑）、主光（從預設視角的方向略往上打，看得到的那面最亮——太高的話朝下的上臂整段
落在陰影裡，顏色暗到跟圖例對不上）、輪廓光（投手側後上方，勾出背面的邊，跟背景拉開）。本壘板、格線、地面微光
是 `MeshBasicMaterial`／`LineBasicMaterial`，不受光源影響；棒球模型沿用 glb 自帶的材質。場景是 z-up，
`HemisphereLight` 的天空方向要手動設成 +z（預設是 +y）。three r155 起沒有舊版光照模式，強度比參考實作（r128）
的 0.85／0.55 高才亮得起來。

## 缺值

規範第 6 節：某幀某關節為 `null` → 該關節與相連骨頭該幀不畫；整幀全 `null` → 整幀骨架不畫，
**不沿用上一幀**；`ball` 為 `null` → 該幀不畫當前球。球與關節（含球棒）互相獨立判斷，缺一個
不影響另一個。缺測骨頭（任一端為 `null`）的兩端寫成同一點、退化成零長線段（不會被光柵化），
缺測關節把 `InstancedMesh` 的 instance scale 設為 0，木棒則設成不可見。

## 拖尾規則

固定 20 顆物件池（每顆是一個 `Group`，`name = ball-trail-${age}`），純取樣邏輯在 `core/ballTrail.ts`：
顯示第 `i` 幀時第 `age` 顆（0～19）取 `frames[i − age].ball`，缺值或負索引就隱藏該顆，
**不往更早的幀找補**——這保證拖尾只由「目標幀」決定、不累積歷史，播放、拖曳、逐幀、
跳至擊球、循環回開頭都自然正確，換事件時拖尾自然換成新事件的（`setSwing()` 之後下一次
`setFrame()` 就會重算）。

`freshness = 1 − age / 19`；場景端把它換成容器 `scale = 3.7 × (0.2 + 0.8 × freshness)`（球本身是
單位半徑，所以等效顯示半徑就是 `3.7 × (0.2 + 0.8 × freshness)` cm）與材質 `opacity = 0.15 + 0.85 × freshness`。
`20`／`3.7`／`0.2` 都是**顯示設定，不是量測值**（`core/ballTrail.ts` 的具名常數）。只有
age 0（最新、不透明）開 `depthWrite`，其餘半透明球不比深度，避免互相遮擋出現排序問題。

### 球的外觀：刻意偏離規範

規範要求「球用與球棒不同的紅色」。本專案的 showcase 改用 `baseball-spin` 同一顆棒球模型
（白球紅縫線，`public/models/baseball_detail.glb`）畫全部 20 顆，這是專案端的決定，不是規範。做法：

- 模型載入後先用 `../baseball-spin/core/normalize-model.ts` 歸一化成單位球，再複製 20 份；
  幾何共用，材質逐顆複製，才能各自設透明度
- 模型晚一步到手時，先畫單位半徑的紅球佔位，到手後原地換掉並依目前幀重套一次
- **沒傳 `ballModelUrl`、或模型載入失敗，就維持紅球**——也就是規範的預設畫法，畫面不會壞
- 換上模型後 `SwingScene` 呼叫 `onBallModelLoaded`，圖例才從紅球改成白球；載入期間與失敗時圖例都是紅球
- 模型到手時元件已卸載，就直接釋放模型的幾何、材質與貼圖，不留在顯示卡記憶體裡

代價：預設視角下球只有幾個像素，要拉近才看得到縫線；淺色畫布上白球拖尾的對比比紅球弱。

## 相機與取景

`core/swingFraming.ts` 掃描**整段動作**，收集要框進畫面的點——只在載入、換事件、切視角時算
（`setSwing()`／`setView()` 內），播放中不重算，避免空間跟著當下幀「呼吸」：

- **全景**（預設）：所有有效關節（含球棒兩點）與所有有效球體座標——規範：「縮放視角時將骨架與有效球體座標
  共同納入範圍」
- **打者特寫**：只有人體關節（`bat_*` 以外）。球棒在預備與收棒時揮到頭頂上方，連它一起框就跟全景差不多大，
  所以特寫讓球棒的最高處與球可以出框。這是使用者自己切過去的視角，預設仍是全景
- **側面／投手方向／俯視**：快捷視角，框的點同全景（含球），只換看的方向，使用者不必每次自己拖到適合的角度
- 每種都另外加上本壘板的五個頂點：板子在打者腳前、畫面最下方，只框關節時常被裁掉一半
- 全缺時退回 0～100 cm 方盒的兩個對角，相機才有地方看

各視角的相機方向在 `SWING_VIEW_EYE`（相對注視點；+x 一壘、+y 投手、+z 上）：

| 視角 | 方向 | 用途 |
|------|------|------|
| 全景、打者特寫 | `(2.0, −2.4, 1.0)` | 一壘側、捕手後方、略高——右打者站三壘側、面向 +x，看得到揮棒正面與弧線 |
| 側面 | `(1, 0, 0.12)` | 一壘側平視，跨步方向在畫面上是左右，看跨步距離與球棒高低 |
| 投手方向 | `(0, 1, 0.3)` | 從投手的位置往本壘看 |
| 俯視 | `(0, −0.12, 1)` | 幾乎正上方，看打者與球相對本壘板的位置。稍微往捕手側偏，畫面「上」才穩定指向投手（正上方時相機 up 與視線平行，方向不定） |

曾經考慮過的「預設就讓打者占畫面 65–75%」做不到：全景上方的空白是球棒在預備與收棒時舉過的範圍，
不是球造成的；要更大只能讓球棒最高處出框（就是打者特寫）或讓鏡頭跟著動作縮放（空間會「呼吸」），
而且預設不含球會違反規範的取景規則。所以預設維持全景，特寫留作一鍵切換。

相機用 `Viewport.framePoints()`（`../scene3d/core/viewport.ts` 的 `fitPointsInView`）依**點本身**取景，
並把注視點挪到點的投影範圍中心，四周留白 1.12 倍（四角還要放圖例、提示與按鈕）。以前用方盒的八個角取景：
打者在三壘側、球從投手方向來，方盒的遠上角是一片空，框進去打者只剩畫面高度的三成；改成框點以後，
全景約五成、打者特寫約六成。注意全景是框**整段動作**：擊球那一幀球棒放低，畫面上方會空著，那是預備與收棒時
球棒揮過的地方。

場景參照物照參考實作，都是**裝飾，不是資料**：

- 本壘板：`../baseball-field/core/fieldGeometry.ts` 的 `HOME_PLATE_POINTS`（官方 17 吋，參考實作寫的
  21.6／43.2 是取整值），扇形三角化、雙面、不透明，外加一圈邊框——淺色畫布上白板子沒邊框會看不見；
  深色畫布上用淺灰而不是純白，免得成為畫面上最亮的東西
- 地面格線：只畫在地上（不像 `pitch-pose` 的軸盒三面都有、還帶刻度），以本壘板尖端為中心、每格 20 cm，
  只畫半徑 300 cm 內，從 150 cm 起往外漸層變透明。整片鋪到地平線時，遠處的細線擠成一片灰，
  會跟骨架搶注意力；打者站在離本壘板 1.5 m 內，漸層從那之外才開始。每格拆成獨立線段、逐頂點給 rgba
  （`GridHelper` 一條線只有一個顏色，畫不出漸層；用透明度而不是混背景色，是因為背景本身是漸層），
  範圍固定、不隨事件改變
- 地面微光：本壘板周圍半徑 320 cm、由中心往外淡出的亮面（放射狀透明度貼圖），像打在地上的燈
- 背景：上暗下亮的漸層（2×256 的 canvas 當 `scene.background`，three 會鋪滿畫面），不是單色
- 指向投手的箭頭：本壘板前方 60 cm 起、長 45 cm。拿掉軸盒後畫面上沒有軸標籤，
  只剩它標出 +y 是投手方向

半透明物件的先後靠 `renderOrder`：微光墊底（−2）、格線其次（−1），拖尾的球最後疊上去；
不指定的話 three 依距離排，遠處的球可能被後畫的格線蓋過。

## 配色

兩套配色都在 `core/swingTheme.ts` 的 `SWING_THEME`（純資料，沒有 three），場景與圖例共用同一份，
**換色只改這一個檔**：

| 用途 | 深色畫布 | 淺色畫布 |
|------|---------|---------|
| 背景漸層（頂 → 底） | `#0b0e13` → `#1b2029` | `#f3f5f8` → `#dce2e9` |
| 左半身四肢 | `#7fa8f8` | `#2f6bdb` |
| 右半身四肢 | `#f08aa8` | `#c7406c` |
| 軀幹 | `#c3cbd6` | `#56606f` |
| 頭部 | `#7d8798` | `#9aa3b1` |
| 關節 | 所屬部位色往白色混 45%（`JOINT_TINT`） | 同左 |
| 球棒（再乘上木紋、加亮光漆） | `#d39a55` | `#b9803a` |
| 本壘板（填色／邊框） | `#cdd3da`／`#5c6778` | `#ffffff`／`#94a3b8` |
| 紅球（沒用棒球模型時） | `#ef4444` | 同左 |

配色原則：

- 背景不用純黑、純白：漸層加地面微光，像在攝影棚裡看；淺色背景是淺灰，放在深色頁面裡才不刺眼
- 視覺層級：四肢帶彩度最搶眼 → 軀幹是不帶彩度的淺灰 → 頭部最淡。軀幹若也帶彩度，眼睛會先看到肩髖的四邊形，
  看不到手腳在做什麼
- 骨頭是 3px 細線，面積小，深色畫布上整組比粗圓柱時期亮一階才看得清楚（參考實作的骨頭是近白的 `#dce2e6`）
- 左右兩色飽和度壓低、明度相近，份量相當；避開球棒的木頭色與規範球的紅（規範：球用與球棒不同的紅色），
  紅綠色盲下藍與玫瑰仍分得開。單元測試會檢查兩套配色的左、右、球棒、紅球互不相同
- 球棒是蜂蜜色的木頭，不用飽和的黃——飽和的黃加上亮光漆看起來像塑膠
- 淺色整組換深一階，近白底上才看得清楚
- 地面格線再淡一階（深色 9%、淺色 8% 不透明），讓人體與本壘板更突出

擊球事件在整個介面一律用琥珀色（Tailwind `amber`，Nuxt UI 的 `warning`）：畫布上的「擊球瞬間」標籤、
時間軸的「擊球」刻度、跳至擊球按鈕、相對時間的「擊球 0 ms」。一般操作維持全站主色，不另外搶焦點。

元件本身只吃 `dark` prop，換配色時骨架整組重建（顏色在建構時寫進 instance 色）。本專案 showcase 預設跟著頁面
（整站固定深色），控制列的「淺色畫布」開關只切這個畫布，頁面其他部分不動。

`BatterSwing3d.vue` 內的圖例（HTML 絕對定位疊在畫布左下角，`pointer-events-none` 不擋 OrbitControls 拖曳）
直接讀 `SWING_THEME` 用 inline style 上色，不另外維護一組 Tailwind class，所以不會跟場景對不上。
骨頭與球棒畫成短線、球畫成圓點，對得上畫面上的形狀；棒球模型真的換上去後「球」才畫成白球（淡灰外框），
模型還沒到手或載入失敗時跟畫面一樣是紅球——以前的白底紅圈會讓人以為畫面上有紅色的東西。
圖例固定顯示「球」，即使這筆結果沒有任何球體座標（`hasBallField: false` 的舊格式）。
